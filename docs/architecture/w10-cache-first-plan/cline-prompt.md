> 用法：每批复制一次"提示词正文"，只改两处——标题里的批次号、必读文件第 2 条的路径。
> 批次顺序：C1 → C2 → C3 → C4 → C5（C2 依赖 C1 的度量口径；C3 依赖 C2 的
> system 构造状态；C4 依赖 C2/C3 的消息形状；C5 收口。**不要乱序，不要跳批**）。
> 前置条件：tag `baseline-pre-w10` 已打（未打则先在主会话执行：
> `git tag -a baseline-pre-w10 -m "W9 收官基线，W10 缓存优先系列起点"`）。

## 提示词正文（复制以下全部内容）

````markdown
# Erza 实施任务 —— 批次 W10-C<N>（<本批主题>）

## 角色与背景

你是 Erza 项目的资深 Python 实施工程师。项目定位：小型企业长期使用的业务智能体（单用户），核心诉求是高效、精简、易维护。本任务是一个五批次"缓存优先"改造计划中的**一个批次**：独立实施、独立验证、独立提交，完成即停。

改造目标一句话：让发给 LLM 的请求在会话内保持字节稳定的前缀，把上下文缓存命中率从基线提到 90%+。本批只做任务书里的事。

工作目录：D:\MyProject\Erza

## 第一步：必读文件（按顺序，实施前读完）

1. `docs/architecture/w10-cache-first-plan/00-overview.md` —— 计划总览与全局约束（重点第 2 节设计原则、第 4 节全局约束）
2. `docs/architecture/w10-cache-first-plan/<本批任务书文件名>` —— **本批次任务书（唯一实施依据）**

任务书自包含：包含现状锚点、改动方案、测试要求、禁改清单、验收自检。你的全部实施范围以任务书为准。

## 实施纪律（优先级高于任何效率考虑）

### 四种情况立即停止并报告（禁止猜测着继续）

1. 任务书中任何"现状锚点"与代码实况不符（符号找不到、行号漂移过大、结构对不上）
2. 完成任务必须触碰"禁改清单"内的文件或逻辑
3. 测试无法全绿且原因不明——**禁止为让测试通过而弱化断言或删改既有测试**（任务书明确允许更新的除外，逐条列出理由）
4. 发现任务书未提及的可疑行为（疑似 bug、疑似安全漏洞）——只记录进报告，不动手修

### 全局红线（完整版见 00-overview.md 第 4 节）

1. **W0-W9 受保护成果语义不得触碰**：可信证据管道、三态审批门、runtime_checkpoint 链路、LazyToolRegistry 装载语义、McpRuntime/SubagentManager 组合根所有权、activate_plan 激活器语义
2. **提示词内容不丢失**（W10 特别）：本系列所有改动是内容**搬家**（system → 尾部/消息），每轮 LLM 请求中召回、notes、跨会话记忆、归档摘要必须仍然全部可见
3. **定位用符号**（类名/函数名/参数名），任务书中的行号只是编写时参考值
4. **不引入新抽象**：无新配置项、无新事件、无新 Port/Adapter、无新持久化格式
5. **不加计划外功能**：不顺手重构、不修复范围外问题、不写解释"改了什么"的注释
6. C5 批次特别红线：**零生产代码改动**——若发现必须改生产代码才能让测试通过，立即停止报告

### Git 纪律

- 单批单 commit；禁止 `git add .`，只 add 明确路径
- 禁止混入 `.tmp-*`、临时报告、无关文件
- commit 消息：`perf(w10-N): <一句话主题>`（C5 用 `test(w10-5): ...`）

## 执行流程

1. 通读两份文件 → 逐条核对任务书"现状锚点"与代码实况，记录核对结论
2. 一致 → 严格按任务书"改动"节实施，范围外一行不动
3. 实现任务书"测试要求"节的**全部**新测试（一条不落）
4. 验证门（全部通过才算完成，未过不得 commit）——**必须用项目 venv 的 Python 3.12**：
   - `.venv\Scripts\python.exe -m pytest tests/ -q` → passed ≥ 4005，failed 集合**恰好等于** `tests/agent/test_tool_hint.py` 的 3 个既有失败（路径缩写相关、与本系列无关的已知问题）——除此之外任何新失败都算不过
   - `.venv\Scripts\python.exe -m ruff check erza/` → 零输出
   - `.venv\Scripts\python.exe -m ruff format --check <本批改动过的 erza/ 源文件>` → 零输出（format 门只查本批改动文件；仓库另有 11 个冷文件基线即未格式化，与本系列无关，**禁止顺手格式化**）
   - 警告：不要用系统默认 python（3.10，缺 typing.Self，收集阶段会报 ImportError，那是环境问题不是代码问题）
5. 按明确路径 `git add` 后 commit
6. 输出批次报告（格式见下）
7. **完成即停**：不继续后续批次，不优化其他文件，不等用户追问就结束

若单次无法完成全部内容：明确报告已完成到哪一步，未过验证门不得 commit，不要留下说不清的半成品（半成品一律 `git checkout -- <files>` 回退后再报告）。
````

## 中断续接规则（已知风险：自主代理在收尾阶段可能静默挂断）

1. 怀疑中断时先 `git status` + `git diff` 判断半成品范围
2. 未 commit 的半成品：`git checkout -- <files>` 回退后重新起批，**不要在半成品上续写**
3. 已 commit 但验证门未过：`git reset --soft HEAD~1` 退回暂存区检查，确认后回退重做
4. C2 → C3 → C4 → C5 有序依赖，前批未合并不得起后批
